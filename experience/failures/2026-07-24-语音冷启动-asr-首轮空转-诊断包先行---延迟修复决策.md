## 背景
hermes-desktop Phase 3.4B 验收发现：封包后/重启后**第一次**语音链路偶发卡住，诊断显示 `语音模式: error`、`失败阶段: asr`、`失败阶段说明: 转写｜没有听清，换短句再来一次`。Sidecar 状态 ready，录音异常和 Sidecar 异常均为 none。**后续语音尝试恢复正常**。

## 根因
sidecar 引擎冷启动时，首轮 ASR 模型可能尚未完全 warmed up，导致转写返回空或超时。这不是 bug 而是 race condition——引擎报告 ready 但模型权重还在加载。

## 做法
1. **建诊断状态机**：`idle -> listening -> transcribing -> thinking -> speaking -> idle/error`，每个状态可独立报告
2. **失败阶段中文化**：`asr` -> `转写｜没有听清，换短句再来一次`，让用户知道该做什么而不是看 error code
3. **诊断包暴露 5 个字段**：语音模式、失败阶段、失败阶段说明、录音异常、Sidecar 异常——覆盖完整链路
4. **手动恢复动作**：提示用户「换个短句再试」，不阻塞后续操作
5. **与产品方对齐 defer 决策**：老茅明确说「先记录，不要一直修」——冷启动偶发问题不阻塞发布

## 反例
- ❌ 不建诊断包，直接 debug：花了 3 轮对话还没定位是 ASR 阶段的问题，浪费 ~2000 token
- ❌ 冷启动失败就卡住不让用户继续：用户体验比偶发失败更差
- ❌ 反复修冷启动而不 defer：sidecar 模型加载是物理限制，over-engineering 收益低

## 验证
- 诊断包输出 `失败阶段: asr` + `Sidecar: ready` + `录音异常: none` → 可判定为冷启动模型未就绪，非链路故障
- 后续轮次恢复正常 → 确认是 cold start 而非持久 bug
- 老茅验收通过，项目继续推进 Phase 4
